Parte 1 · ModelagemHierarquia dos modelos de dados

Os modelos de dados evoluíram buscando mais semântica — mais capacidade de representar significado, e não só estrutura. A ordem, do menos ao mais semântico:

Sistemas de arquivos → Hierárquico → Relacional → Entidade-relacionamento → Semântico → Orientado a objetos → Relacional estendido (objeto/relacional)

FonteAdaptado de Rob e Coronel (2016, p. 48). O relacional estendido (também chamado objeto-relacional) fica no topo por juntar a robustez do modelo relacional com conceitos de objetos.

Níveis de abstração

Um mesmo banco é enxergado de formas diferentes dependendo de quem olha. Da aula (Rob e Coronel, 2016, p. 56):

ModeloNível de abstraçãoFocoIndependência
ExternoAltoVisões dos usuários finaisHardware e software
ConceitualRazoavelmente altoVisão global dos dadosHardware e software
InternoRazoavelmente baixoModelo específico de banco de dadosDependente de software · independente de hardware
FísicoBaixoMétodos de armazenamento e acessoDependente de software e hardware

Pegadinha comumDo externo para o físico o nível de abstração cai e a dependência de hardware sobe. O conceitual é o único totalmente independente de um SGBD específico — é o nível do diagrama entidade-relacionamento.

O modelo relacional

Idealizado por Edgar Frank Codd, pesquisador da IBM, em 1970, no artigo "A Relational Model of Data for Large Shared Databanks".

Princípios: os dados são organizados em tabelas (relações), compostas por linhas (tuplas) e colunas (atributos).

  • Cada linha (tupla) é uma ocorrência única de entidade no conjunto.
  • Cada coluna representa um atributo e tem nome próprio; todos os valores de uma coluna respeitam o mesmo domínio.
  • Cada interseção linha × coluna é um único valor.
  • A ordem das linhas e colunas não importa para o SGBD.
  • Toda tabela precisa de um atributo (ou combinação) que identifique exclusivamente cada linha.

FonteRob e Coronel (2011, p. 68).

Dependência funcional

Uma chave é um atributo (ou conjunto de atributos) que determina outros atributos.

CPF → Nome, Data de nascimento

Princípio da determinação funcional: A → B significa que cada valor de A determina um, e somente um, valor de B — B é funcionalmente dependente de A.

Dependência funcional completa, com chave composta: se D depende de (A,B,C) mas não de nenhum subconjunto próprio dessa chave, então D tem dependência funcional completa em relação a (A,B,C).

FonteRob e Coronel (2011, p. 71).

Tipos de chave

ChaveDefinição
Super chaveAtributo (simples ou composto) que identifica uma tupla.
Chave candidataSuper chave mínima (irredutível) — nenhum subconjunto dela também é super chave.
Chave primáriaChave candidata escolhida para identificar a tupla. Não pode ser nula.
Chave secundáriaAtributo (simples ou composto) usado para recuperação de dados.
Chave estrangeiraAtributo que coincide com atributos de outra tabela. Pode ser nula.

Regras de integridade

Integridade de entidade: todos os valores de chave primária são únicos e não podem ser nulos. Exemplo: nenhuma pessoa pode ser cadastrada sem CPF.

Integridade referencial: uma chave estrangeira pode ser nula, desde que não faça parte da chave primária daquela tabela. Todo valor não nulo de chave estrangeira deve referenciar um valor de chave primária existente — senão a referência "aponta para o nada".

Operadores e relacionamentos

Operadores do conjunto relacional: união, interseção, diferença, produto, junção e divisão, além de dois que costumam ser confundidos:

  • Seleção — recorta algumas linhas da tabela (filtro por condição).
  • Projeção — recorta algumas colunas, mantendo todos os valores dessas colunas.

Relacionamentos

  • 1:1 um para um — uma pessoa possui um CPF.
  • 1:M um para muitos — uma casa tem muitos quartos.
  • M:N muitos para muitos — disciplinas possuem muitos alunos, e alunos cursam muitas disciplinas.

Índices

Pergunta da aula: se uma tabela tem 1 bilhão de registros, qual a forma mais eficiente de achar um registro específico? Resposta: índices — estruturas que evitam varrer a tabela inteira linha por linha.

As regras de Codd

Critérios que definem o que é, de fato, um SGBD relacional (Rob e Coronel, 2011, p. 99). Não é preciso decorar o número de cada regra, mas reconhecer o conteúdo:

RegraIdeia central
InformaçãoTodo dado é representado como valor de coluna, em linha, dentro de tabelas.
Garantia de acessoTodo valor é acessível via tabela + chave primária + coluna.
Valores nulosNulos são tratados de modo sistemático, independente do tipo de dado.
Catálogo dinâmicoMetadados são armazenados e consultados como dados comuns, via linguagem relacional.
Sublinguagem de dadosDeve existir uma linguagem declarativa única para definição, manipulação, integridade, autorização e transações.
Atualização de visualizaçãoToda visão atualizável deve poder ser atualizada pelo próprio sistema.
Inclusão/alteração/exclusão de alto nívelSuporte à manipulação de dados como conjunto, não só linha a linha.
Independência físicaMudar o armazenamento físico não afeta aplicações.
Independência lógicaMudanças de estrutura que preservam os valores (nova coluna, reordenar) não afetam aplicações.
Independência de integridadeRegras de integridade ficam no catálogo do sistema, não no nível da aplicação.
Independência de distribuiçãoUsuários e aplicativos não sabem (nem precisam saber) onde os dados estão fisicamente.
Não transposição de regrasMesmo com acesso de baixo nível, as regras de integridade não podem ser burladas.
Regra zeroPara ser relacional, o SGBD deve gerenciar os dados exclusivamente por recursos relacionais.

Parte 2 · ObjetosOrientação a objetos

Paradigma que surgiu nos anos 80, quando tipos primitivos e estruturas simples deixaram de ser suficientes para as necessidades dos desenvolvedores. Um programa passa a ser uma coleção de objetos que trocam mensagens entre si — e essa troca altera o estado de cada objeto.

A vantagem central é mapear o mundo real em software: um objeto Pessoa tem atributos (altura, peso, cor dos olhos) e comportamentos (caminhar, falar, escrever).

Elementos-chave

  • Herança
  • Tipos de dados abstratos
  • Vinculação dinâmica de chamadas de métodos

Conceitos

ConceitoO que é
ClasseDeclaração de um tipo abstrato que encapsula constantes, variáveis e métodos. Pode ter subclasses.
ObjetoInstância de uma classe: tem um conjunto de operações (métodos) encapsuladas e um estado, determinado pelos valores de seus atributos.
Classes abstratasFornecem apenas a estrutura (nomes de métodos e atributos) sem implementação — os métodos têm só a assinatura. Não podem ser instanciadas.
Classes concretasImplementam os métodos e podem ser instanciadas.
HerançaUm objeto herda atributos e métodos de outro.
PolimorfismoMesma mensagem/método se comporta de formas diferentes conforme o objeto que a recebe.
InterfacesContrato de métodos que uma classe se compromete a implementar.
EncapsulamentoEsconder o estado interno do objeto, expondo-o só pelos métodos.

Mensagem é a chamada de um método. Construtores e destrutores são métodos especiais executados, respectivamente, quando um objeto é instanciado ou destruído.

Atributos se dividem em: atributo de objeto (dado individual de cada instância) e atributo de classe (dado compartilhado entre todos os objetos da mesma classe).

Visibilidade

  • Public — acessível de qualquer lugar.
  • Protected — acessível pela própria classe e suas subclasses.
  • Private — acessível só dentro da própria classe.

Herança múltipla

Linguagens como C++ permitem que um objeto herde de dois ou mais objetos. Linguagens como Java não permitem herança múltipla de classes (só de interfaces).

Bancos de dados orientados a objetos

Pergunta motivadora: como persistir objetos do código em um banco relacional? Em vez de converter objetos em tabelas, por que não guardar os objetos diretamente? Resposta: um banco de dados orientado a objetos — um SGBD que armazena as informações como objetos, do mesmo jeito que são usados em linguagens OO.

Comparação com o banco relacional

Sistema de biblioteca, com tabelas Livros, Autores, Editoras:

  • Banco relacional — para buscar os autores de um livro, é preciso join entre tabelas.
  • Banco orientado a objetos — uma classe Livro contém diretamente um objeto Autor e um objeto Editora. Acessa-se o autor com livro.autor.nome, sem join.
Vantagens

Alinhamento natural com a programação orientada a objetos · reduz complexidade do código (menos mapeamento objeto-tabela) · melhor para dados ricos e complexos · boa performance quando os objetos estão muito interligados.

Desvantagens

Pouca padronização — não existe uma linguagem única para objetos, como o SQL é para o relacional · menor popularidade, menos ferramentas e suporte · dificuldade de integração com sistemas legados que usam SQL · em muitos casos, bancos relacionais ou NoSQL são mais eficientes.

Exemplos de SGBD orientado a objetos

  • db4o — para Java e .NET.
  • ObjectDB — banco comercial para Java.
  • Versant Object Database — usado em aplicações corporativas.
  • GemStone/S — voltado para Smalltalk.

Parte 3 · TempoBancos de dados temporais

Bancos de dados tradicionais armazenam apenas o estado atual. Para análises históricas e previsões, é preciso registrar informação junto ao fator tempo — recuperando dados do passado e planejando cenários futuros.

Um banco de dados temporal registra informações associadas ao tempo, permite acompanhar mudanças e históricos completos, suporta consultas por intervalo e validade temporal, e cada registro pode ter um atributo temporal associado. Exemplo: o salário de um funcionário em diferentes anos.

Vantagens

Histórico completo e rastreável · consultas sobre o passado e projeções futuras · suporte a auditorias e conformidade regulatória.

Desvantagens

Aumento do volume de dados · maior complexidade nas consultas · nem todos os SGBDs suportam nativamente.

Tipos de tempo

TipoO que representa
Tempo de transaçãoQuando o dado foi registrado no banco — o momento de inserção ou alteração. Usado para auditoria e controle de alterações.
Tempo de validadeO período em que a informação é verdadeira no mundo real. Exemplo: contrato válido de 01/01/2020 a 31/12/2022. Permite consultas históricas reais.
Tempo bitemporalCombina transação e validade — visão completa da evolução dos dados, essencial para auditorias detalhadas.

Características

  • Armazenamento de histórico — mantém versões passadas, não só o estado atual; permite consultar "como era" em determinado momento.
  • Dimensão temporal — associa datas ou intervalos de validade aos registros.
  • Versionamento automático — alterações não sobrescrevem valores anteriores; cada versão fica registrada com sua validade.
  • Consistência temporal — deve garantir integridade em relação ao tempo (ex.: não permitir intervalos sobrepostos em certos contextos).
  • Auditoria e rastreabilidade — permite verificar quem alterou, quando e o quê; crítico em áreas reguladas (financeiro, jurídico, saúde).
  • Maior volume de dados — manter histórico tende a armazenar muito mais informação que um banco convencional.

Consultas temporais na prática

Consultas temporais usam operadores específicos — por exemplo, encontrar dados válidos em certa data. Alguns SGBDs oferecem recursos SQL dedicados. No PostgreSQL, a extensão temporal_tables versiona automaticamente uma tabela.

-- Criar a tabela de funcionários
CREATE TABLE funcionario (
    id SERIAL PRIMARY KEY,
    nome TEXT,
    salario NUMERIC
);

-- Ativar o versionamento temporal
SELECT create_history_table('funcionario', 'funcionario_hist');
-- Qual era o salário de João em 01/01/2022?
SELECT nome, salario
FROM funcionario_hist
WHERE nome = 'João' AND
tstzrange(val_period_start, val_period_end) @> TIMESTAMP '2022-01-01';
-- Todas as versões de salário de João, em ordem
SELECT nome, salario, val_period_start, val_period_end
FROM funcionario_hist
WHERE nome = 'João'
ORDER BY val_period_start;

AtençãoO operador @> testa se o intervalo tstzrange(...) "contém" o instante informado. A tabela de histórico guarda uma linha por período de validade, não uma por alteração isolada de coluna.

Cenários de utilização

  • RH — histórico salarial, cargos ocupados, benefícios ativos em determinada época.
  • Finanças — transações e saldos ao longo do tempo, reconciliação, auditoria de movimentações.
  • IoT — séries temporais de sensores, análise de tendências, identificação de anomalias.

SGBDs com suporte temporal

  • Oracle — Flashback.
  • SQL Server — System-Versioned Tables.
  • PostgreSQL — extensões (como temporal_tables).
  • DB2 — suporte bitemporal.
  • TimescaleDB — séries temporais.
  • InfluxDB — NoSQL temporal.
